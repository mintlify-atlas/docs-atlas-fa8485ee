`HealResponse` is the complete record of everything that happened during a healing run. It is returned synchronously from the `/heal` endpoint once the self-healing loop exits — either because all tests passed, all iterations were exhausted, or a fatal error occurred. Beyond the final code, the response includes the full ordered log trail, per-test status mappings, a list of file patches, and a pre-rendered Markdown audit report ready to post as a GitHub PR comment.

## Core Outcome Fields

<ResponseField name="success" type="boolean" required>
  `true` if all generated `pytest` assertions passed in the final sandbox run; `false` if the pipeline exhausted its maximum iterations or encountered a fatal error without achieving a clean test run.
</ResponseField>

<ResponseField name="iterations_used" type="integer" required>
  Number of Healer Agent iterations that were actually executed. Will be `0` if the very first sandbox run already passed (no healing needed), up to `MAX_HEALING_ITERATIONS`.
</ResponseField>

<ResponseField name="final_code" type="string" required>
  The complete source code of the target file as it existed at the end of the pipeline — either the original code if no patch improved it, or the last patch the Healer agent applied.
</ResponseField>

<ResponseField name="generated_tests" type="string" required>
  The full `pytest` test suite synthesized by the Test Engineer agent. This is the verbatim Python source that was written to the sandbox and executed during every iteration.
</ResponseField>

## Language and Targeting

<ResponseField name="language" type="string" default="python">
  Target programming language — mirrors the value from `HealRequest`.
</ResponseField>

<ResponseField name="failing_file" type="string" default='""'>
  Relative path to the source file that was targeted for healing (e.g. `compound_interest.py`). Matches the `file_path` from the request, defaulting to `target.py`.
</ResponseField>

<ResponseField name="test_target" type="string" default='""'>
  Relative path to the generated test file that was executed in the sandbox (e.g. `test_target.py` or `tests/test_compound_interest.py`).
</ResponseField>

<ResponseField name="ast_dependencies" type="array of strings" default="[]">
  List of source file paths that the AST analyzer identified as interdependent with the failing file. For single-file healing this is always `[source_file, test_filename]`. For repository-level healing it reflects the full dependency graph.
</ResponseField>

## Patches and Aliases

<ResponseField name="patches" type="array of FilePatch" default="[]">
  List of `FilePatch` objects representing each file that was changed during the healing run. A patch is only appended when `final_code != original buggy_code`. See [FilePatch schema](/api-reference/schemas/file-patch) for field details.
</ResponseField>

<ResponseField name="patched_code" type="string" default='""'>
  Convenience alias: the `patched_content` from the first entry in `patches`, or an empty string if no patch was applied. Auto-populated by `model_post_init` when `patches` is non-empty.
</ResponseField>

<ResponseField name="iterations" type="integer" default="0">
  Alias for `iterations_used`. Both fields are kept in sync by `model_post_init`; prefer `iterations_used` in new integrations.
</ResponseField>

<ResponseField name="model_name" type="string" default='""'>
  Name of the Gemini model used for both the Test Engineer and Healer agents (e.g. `"gemini-3.6-flash"`). Mirrors `settings.PRIMARY_MODEL`.
</ResponseField>

<ResponseField name="model_used" type="string" default='""'>
  Alias for `model_name`. Both fields are kept in sync by `model_post_init`.
</ResponseField>

<ResponseField name="max_iterations" type="integer" default="3">
  The `MAX_HEALING_ITERATIONS` ceiling that was configured when the pipeline ran.
</ResponseField>

## Logs and Diagnostics

<ResponseField name="logs" type="array of LogEntry" default="[]">
  Chronological list of `LogEntry` objects emitted at every pipeline step. Useful for debugging, observability dashboards, and building audit trails. See [LogEntry schema](/api-reference/schemas/log-entry) for field details.
</ResponseField>

<ResponseField name="failure_logs" type="string" default='""'>
  The raw `pytest` stdout/stderr captured during the **first** failing sandbox run. This is the original traceback before any Healer agent intervention.
</ResponseField>

<ResponseField name="audit_report" type="string" default='""'>
  A pre-rendered Markdown string containing the full healing audit report — iteration count, model, AST dependencies, per-test before/after status table, and the final patched code. Identical to the content posted as a GitHub PR comment by the GitHub App integration.
</ResponseField>

<ResponseField name="test_summary" type="object" default="{}">
  A dictionary mapping each `pytest` test case identifier to its initial and final status. Keys are test node IDs (e.g. `"test_target.py::test_zero_rate"`). Each value is an object with two keys:

  <Expandable title="test_summary value shape">
    <ResponseField name="initial" type="string">
      Status of the test during the first sandbox run. Either `"Passed ✅"` or `"Failed ❌"`.
    </ResponseField>
    <ResponseField name="final" type="string">
      Status of the test after the last sandbox run. Either `"Passed ✅"` or `"Failed ❌"`.
    </ResponseField>
  </Expandable>
</ResponseField>

## Alias Synchronization

`HealResponse` exposes several aliased fields for backwards compatibility. The `model_post_init` hook keeps them in sync automatically:

```python
def model_post_init(self, __context) -> None:
    if self.iterations == 0 and self.iterations_used > 0:
        self.iterations = self.iterations_used
    if not self.model_used and self.model_name:
        self.model_used = self.model_name
    if not self.model_name and self.model_used:
        self.model_name = self.model_used
    if not self.patched_code and self.patches:
        self.patched_code = self.patches[0].patched_content
```

<Warning>
  Do not rely on only one alias in your integration code. If you are building on top of the AutoFix API, prefer the **canonical** field names: `iterations_used`, `model_name`, and `patches[0].patched_content`.
</Warning>
